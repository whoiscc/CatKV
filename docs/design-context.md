# CatKV 项目上下文

本文记录 CatKV 的项目目标、架构边界与待定方案，供开发时参考。
当前仓库仅包含开发环境和 Rust workspace 骨架，以下存储引擎、网关、复制和分片设计尚未实现。

## 项目目标与约束

- 兴趣性质的分布式通用键值存储，目标是持续公开运行，允许公众施加实际负载，公开性能、故障、恢复和扩容过程。
- 实践源码与二进制版本管理、容器部署、滚动升级、失败重启以及监控。
- 必须能通过分片水平扩容；自行实现核心协议是项目兴趣的一部分。
- 单机存储引擎也从头实现，不依赖 RocksDB 等现成存储系统。实现直观流畅优先，性能其次。
- Storage 只认识 bytes key → bytes value，不理解名字空间；Gateway 对公众提供名字空间、鉴权、限流和键编码。
- Gateway 没有必须从单个实例恢复的持久化业务状态。需要持久化的配置保存在 Storage，Gateway 缓存配置。
- 通常请求路径的鉴权和限流在网关本地完成，不为每次请求增加额外后端存储访问。
- 实际部署要求 KV 节点位于独立物理宿主机。单台开发机上的多个容器仅能模拟逻辑节点，不能验证该物理故障域要求。

## 起步方案（设计提案）

单机设计以 Rust / Linux 本地文件系统为基础，本开发环境据此准备。
第一阶段先实现单机引擎，再逐步接入网关、复制和分片：

1. 一个追加数据文件、内存哈希索引、独占状态的存储线程。
2. 基本 Get / Put / Delete，区分不存在与空 value；记录格式显式编码并校验 CRC。
3. 成功确认前完成持久化；重启顺序恢复；无法解释的完整记录损坏应报告错误。
4. 初期采用暂停式全量压缩，处理文件同步、原子替换和目录同步。
5. 后续可考虑 group commit，再讨论并发读取和在线压缩。

实现引擎时应以无 namespace 的内部键值接口为准，名字空间由 Gateway 处理。

## 尚未锁定的选择

复制的一致性模型与算法、传输协议、分片放置与迁移方案、云厂商、最终节点规模，
以及网关元数据所需的原子接口，都需要后续设计与验收。设计提案不代表已实现功能或已确定的要求。
