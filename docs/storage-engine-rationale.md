# 为什么存储引擎从这个提案起步

当前提案可以理解为一个 Bitcask 风格引擎的 MVP：先验证基本读写、持久化与恢复正确性，
再逐步完善文件管理和并发能力。这符合项目“实现直观流畅优先，性能其次”的原则。

- **单文件追加写**：先减少文件轮换与跨文件恢复的复杂度，代价是文件增长后恢复和整理更慢。
- **内存哈希索引、单线程独占状态**：适合 Get / Put / Delete，让文件与索引的更新顺序容易推理；
  代价是索引占用内存，慢操作会阻塞后续请求。
- **成功确认前持久化、CRC 与顺序恢复**：先建立明确的成功语义和损坏检测规则，接受同步等待与启动扫描的成本。
- **暂停式全量整理**：在数据不再变化时生成新文件并替换，先验证文件同步、替换与恢复流程；
  代价是服务停顿和额外磁盘空间。这里的整理指回收旧记录，不是压缩 value 字节。

可能的演进路线是：**单文件 MVP → 文件分段与轮换 → 在线合并、并发读取与 hint 文件启动加速**。
如果同步开销先成为瓶颈，可以提前考虑 group commit，让一批写入共用一次同步，仍在同步成功后确认。
后续顺序按测量结果调整；多文件在线合并仍需重新设计文件生命周期和崩溃恢复流程。

这条路线参考 [Bitcask 的核心设计](https://riak.com/assets/bitcask-intro.pdf)。
当前及后续阶段均属提案，尚未实现，也未约定必须完整复刻 Bitcask。
项目状态与约束以[设计上下文](design-context.md)为准。
